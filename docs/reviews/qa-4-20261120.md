### 3-2. 불일치 / 명세 공백

- [참고] 쿠키 이름이 API.md에 없다. 실제 이름은 Secure일 때 `__Host-session`, `__Host-setup`이고 `COOKIE_SECURE=0`(로컬 http)일 때는 접두사 없는 `session`, `setup`이다(`sessions.py` `cookie_name`). 프론트는 HttpOnly라 직접 읽지 않으므로 계약 위반은 아니지만, 개발 중 DevTools·curl 확인과 Phase 6 로컬 프록시 설정에 필요하니 API.md "세션 쿠키" 항목에 한 줄 적는다.
- [참고] 가입 토큰 비교 전에 입력값 앞뒤 공백을 제거한다(`given.strip()`, 서버 값도 `normalize_setup_token`에서 `strip`). API.md는 이를 말하지 않는다. 붙여넣기 실수에 관대한 쪽이라 문서에 한 줄만 추가하면 된다.
- [참고] 공통 상한의 수치(분당 300)가 API.md에 없다(`config.py` `DEFAULT_REQUESTS_PER_MINUTE`). 프론트가 알 필요는 없으나, 설정 변경용 환경변수가 없다는 점을 `backend/README.md` 환경변수 표에 적어 두면 헷갈리지 않는다.

- [권장] 복구 코드 형식(`XXXX-XXXX-XXXX-XXXX`, 0/O/1/I 제외)을 검사하는 테스트가 없다. `re.fullmatch(r"([A-HJ-NP-Z2-9]{4}-){3}[A-HJ-NP-Z2-9]{4}", code)`로 10개 모두 확인한다.
- [권장] 입력 규칙(인증) 중 아이디 "앞뒤 공백 제거 후 저장", "제어문자 금지", 비밀번호 1024자 초과 400이 `/setup`에서 테스트되지 않았다(`test_setup_input_validation`은 공백만 있는 값, 65자, 10자 미만만 본다). 또 로그인에서 앞뒤 공백이 있는 아이디(`" tester "`)가 통과하는지(`router.py` 349행 `strip`)도 테스트가 없다.

## 4. 배포 관점

서버 `.env`의 현재 내용은 이 환경에서 확인할 수 없다(확인 불가). 아래는 코드·compose·README 기준의 정적 판단이다.

### 4-1. `SESSION_SECRET`이 없으면 롤백된다 — 동작은 의도대로, 절차 문서가 없다

- 근거: `config.py`가 기동 시 `ConfigError`로 프로세스를 끝낸다 → api 컨테이너가 healthy가 되지 못함 → `depends_on: service_healthy` 때문에 `docker compose up`이 실패 → `deploy.sh`가 직전 SHA(Phase 3 이미지)로 롤백. 값은 오류 메시지에 들어가지 않는다(테스트 있음).
- Phase 2 `deploy/README.md` 6절은 "`openssl rand -hex 32` 출력을 `SESSION_SECRET`에 붙여넣는다"고 안내했으므로 서버 `.env`에 이미 있을 가능성이 높다. 다만 값이 자리표시자 그대로이거나 31자 이하이면 롤백된다.
- [필수, PR 전] **`deploy/README.md`에 Phase 4 서버 작업 절차가 전혀 없다**(`SESSION_SECRET` 언급은 6절 표뿐, `SETUP_TOKEN`은 없음). CLAUDE.md "서버에서 사람이 직접 실행해야 하는 일은 `deploy/README.md`에 명령과 함께 문서로 남긴다"에 해당한다. 담당 infra. 최소 내용:
  1. 승인 전 `.env` 점검 `chk`: `SESSION_SECRET`이 있고, 자리표시자(`change-me-...`)가 아니고, 32자 이상 (값은 출력하지 않고 ✅/❌로). `SITE_DOMAIN` 존재도 함께.
  2. `SETUP_TOKEN` 처리(4-2 참고): 넣는 시점, 만드는 법, 가입 후 지우는 법.
  3. `.env` 변경이 반영되는 시점: compose는 `env_file`이 바뀌면 다음 `up -d`에서 컨테이너를 다시 만든다 → "다음 배포(같은 SHA 재실행 포함)" 때 반영. 수동 `docker compose up`은 `.env`의 `IMAGE_TAG`가 자리표시자라 쓸 수 없으므로 배포로 반영하게 안내한다.
  4. 배포 직후 확인(사용자 PC에서 curl): `GET /api/health` → `{"status":"ok"}`, `GET /api/auth/status` → `{"setup_required":true,"logged_in":false}`.
  5. 롤백이 일어났을 때 원인 구분: `SESSION_SECRET` 문제인지 DB 권한 문제인지 `docker logs`로 보는 명령(값이 노출되지 않는 형태로).
- PR 설명에는 "서버 `.env`에 `SESSION_SECRET` 필수, 승인 전 확인"을 맨 위에 적는다. compose·`deploy.sh`는 바뀌지 않았으므로 "🖐 서버 파일 갱신 필요"와 "⚠️ 배포 경로 변경" 표시는 필요 없다.

### 4-2. `SETUP_TOKEN`이 없으면 가입이 막힌다 — 안전한 기본값이지만 Phase 6 이전에는 가입 수단이 없다

- 근거: 토큰이 없거나 자리표시자·32자 미만이면 `/auth/setup`이 403 `setup_token_not_configured`다. 앱은 정상 기동한다(`test_setup_token_not_configured`). 시작 시 안내 경고가 로그에 남는다.
- [필수, 계획 결정] **Phase 4를 배포해도 가입 화면은 Phase 6에서야 생긴다.** 현재 서버에 올라가는 프론트는 Phase 1 목(mock) 화면이라 가입·로그인 UI가 없다. 따라서 Phase 4 배포 시점에 `SETUP_TOKEN`을 넣으면 "토큰은 있는데 쓸 화면이 없는" 기간이 길어진다. 권장 순서:
  - Phase 4 배포: `SESSION_SECRET`만 확인한다. `SETUP_TOKEN`은 넣지 않는다 → 가입 API는 계속 403으로 닫혀 있다.
  - Phase 6 프론트가 배포되기 직전에 `SETUP_TOKEN`을 넣고 배포 → 가입 화면에서 토큰 입력 → 가입 완료 후 줄을 지우고 다음 배포.
  - 대안: Phase 6 이전에 curl로 직접 가입하려면 README에 단계별 명령(QR의 `secret`을 인증 앱에 수동 입력)이 필요하다. 어느 쪽이든 PLAN에 한 줄 적어 사용자가 결정한다.
- 가입 후 `.env`에서 줄을 지워도 다음 배포 전에는 컨테이너 환경에 남는다. 지우는 즉시 반영되지 않는다는 점을 README 문구에 넣는다(남아 있어도 가입 API는 403 `setup_disabled`).

### 4-4. 데이터 디렉터리·read_only 컨테이너

- 통과 (정적): 앱이 쓰는 곳은 `/data`(서버 `/opt/scrap-app/data`, 소유 10001, 700 — SQLite `-wal`/`-shm` 포함)와 `/tmp`(tmpfs 32MB, SQLite 임시 파일)뿐이다. 코드에서 다른 경로에 쓰는 곳은 없다(로그는 표준출력, `.pyc`는 빌드 때 생성 + `PYTHONDONTWRITEBYTECODE`). `HOME=/tmp`도 유지된다. 새 라이브러리(argon2, pyotp, qrcode)도 디스크에 쓰지 않는다(QR은 메모리에서 SVG 생성).
- 통과 (정적): Phase 3의 `check_database`가 디렉터리 쓰기 권한(WAL 파일 생성에 필요)까지 확인하므로 UID 불일치는 health 503으로 드러난다.
- [참고] WAL 모드가 켜지면 `data/`에 `scrap.db-wal`, `scrap.db-shm`이 생긴다. Phase 8 백업·복원 절차는 `scrap.db`만 복사하면 안 되고 `sqlite3 .backup`(또는 Python backup API)을 쓰거나 세 파일을 함께 다뤄야 한다. 배포 직전 백업은 이미 backup API를 쓰므로 문제없다.
- [참고] 메모리: Argon2 19MiB × 동시 2개 제한(`crypto.py`)이므로 api 384MB 한도에 여유가 있다.

### 4-5. compose·Dockerfile 변경 필요 여부

- 통과: **변경 필요 없음.** (1) 새 의존성은 모두 슬림 이미지용 휠이라는 `requirements.txt` 주석이 맞다면 빌드 단계에 컴파일러가 필요 없다(빌드로 확인, 1절). (2) `command`의 `--workers=1`, `--proxy-headers`, `--forwarded-allow-ips=172.30.80.10`이 그대로 맞다. (3) `env_file: .env`가 `SESSION_SECRET`·`SETUP_TOKEN`·`SITE_DOMAIN`을 api에 모두 전달한다. (4) `mem_limit`, `pids_limit`, `read_only`가 충분하다.
- [권장] 워커를 1개로 유지해야 한다는 제약이 `backend/README.md`에 없다. 가입 대기·로그인 challenge·로그인 실패 횟수가 프로세스 메모리에 있어서 워커나 컨테이너를 늘리면 인증이 깨진다(`memstore.py` docstring에만 있음). README "구조" 절에 "워커 1개 고정(인증 임시 상태가 메모리에 있음), 재시작하면 진행 중인 가입·로그인 2단계가 처음부터 다시"를 한 줄 추가한다.
- [참고] `SITE_DOMAIN`은 api의 허용 출처(`https://<SITE_DOMAIN>`)를 만든다. 서버 `.env`에는 이미 있고 소문자 도메인 형식이어야 한다. 값이 비어 있으면 api는 경고만 남기고 기동하며 브라우저의 POST가 모두 403이 된다 → 4-1의 점검 `chk`에 `SITE_DOMAIN`도 포함한다.

## 5. Phase 6 프론트 연동 때 API.md에 아직 없는 것

API.md에 추가하거나 Phase 6 체크리스트에 옮겨 적을 것. 모두 [권장]이다.

1. **가입 화면의 `setup_token` 입력칸.** 비밀번호처럼 가려서 받고(`type=password`, `autocomplete="off"`), 저장·재사용하지 않으며(localStorage·sessionStorage·URL 금지) 가입 성공·실패 후 상태에서 지운다. "서버 `.env`의 `SETUP_TOKEN` 값"이라는 안내 문구와, `setup_token_not_configured`일 때의 안내("서버에 가입 토큰이 설정되어 있지 않습니다")가 필요하다.
2. **오류 코드별 화면 처리 표.** 서버가 한국어 `message`를 돌려주므로 대부분은 그대로 표시하면 되지만 화면 동작은 코드로 갈라야 한다:
   | 코드 | 화면 동작 |
   |---|---|
   | `unauthorized` (401) | 로그인 화면으로 (이 코드일 때만) |
   | `invalid_credentials`, `invalid_code` (401) | 입력칸 아래 오류 문구, 화면 유지 |
   | `challenge_expired` (400) | 비밀번호 단계부터 다시 |
   | `setup_expired` (400) | 가입 처음부터 다시(QR 재발급) |
   | `totp_reset_expired` (400) | 재설정 처음부터 다시 |
   | `setup_disabled` (403) | 로그인 화면으로 이동 |
   | `setup_token_not_configured`, `invalid_setup_token` (403) | 가입 화면에 안내 문구 |
   | `too_many_attempts` (429) | `Retry-After`(초) 기반 대기 안내, 입력 잠금 |
   | `too_many_requests` (429) | 잠시 후 다시 시도 |
   | `origin_mismatch` (403) | 개발 프록시·허용 출처 설정 오류 안내(운영에서는 나오지 않아야 함) |
   | `db_unavailable` (503), `internal_error` (500), 네트워크 오류 | 재시도 화면 |

   `invalid_input`의 `message`는 일반 문구("입력값이 올바르지 않습니다.")이므로 프론트가 길이·형식(아이디 1~64자, 비밀번호 10자 이상, 코드 6자리)을 먼저 검사해 구체적 안내를 줘야 한다. 이 표를 API.md "오류 코드 정리"에 합치는 것이 좋다.
3. **`/auth/status` 실패 처리**(qa-1 E-3 이월분). 네트워크 오류·429·503일 때 `logged_in: false`로 단정하지 말고 재시도 화면을 보여 준다. 가드는 `setup_required` → 가입, `logged_in` false → 로그인, 그 외 → 앱의 3분기이고 오류는 4번째 상태다. `http.ts`는 401 `unauthorized`일 때 로그인 화면으로 보내고, 작성 중 내용 경고(PLAN Phase 6 항목)와 이어지게 한다.
4. **가입 도중 새로고침·다른 기기.** 가입 대기는 요청한 브라우저의 쿠키에 묶여 있고(10분), QR을 다시 조회하는 API는 없다. 새로고침하면 `/auth/setup`을 다시 불러 새 QR을 받아야 하며(이전 대기 정보는 대체됨) 이미 인증 앱에 등록한 항목은 쓸모없어진다는 안내가 필요하다.
5. **복구 코드 화면.** 서버가 다시 보여 주지 않으므로(조회 API 없음) "복사/저장했음" 확인 뒤에만 닫히게 하고, 가입 확정 응답(`/setup/verify`)과 `totp/reset/verify` 응답 모두 같은 컴포넌트를 쓴다. 코드는 `XXXX-XXXX-XXXX-XXXX`로 표시.
6. **TOTP 같은 구간 재사용 거부.** 가입을 마친 직후 같은 30초 안에 같은 코드로 다시 로그인하면 `invalid_code`가 나온다. 로그인 화면 오류 문구에 "방금 쓴 코드는 다음 코드가 나올 때까지 기다린 뒤 입력"을 넣는다.
7. **입력칸 속성(iOS).** 아이디 `autocapitalize="none" autocorrect="off"`(서버는 아이디 대소문자를 구분하므로 iOS 자동 대문자가 로그인 실패를 일으킨다), 비밀번호 `autocomplete="current-password"`/`"new-password"`, 인증 코드 `autocomplete="one-time-code" inputmode="numeric"`. 실기기 아이폰 확인 항목에 넣는다.
8. **로컬 개발 프록시.** `frontend/vite.config.ts`에는 `/api` 프록시가 없다. Phase 6에서 개발 서버가 백엔드를 부를 때: Vite `server.proxy`로 `/api`를 백엔드로 넘기고, 백엔드는 `COOKIE_SECURE=0`, `ALLOWED_ORIGINS=http://localhost:5173`으로 띄운다(`backend/README.md`의 예시와 일치). `http://localhost`에서는 `__Host-` 접두사 없이 `session`/`setup` 쿠키가 쓰인다.
9. **서비스워커.** PWA 서비스워커의 캐시 대상에서 `/api/*`를 제외한다(세션 목록 등이 오프라인 캐시에 남지 않게, 로그아웃 후 이전 화면이 보이는 사고 방지). 정적 자산만 사전 캐시.
10. **설정 화면 표시값.** 세션 `last_seen_at`은 갱신 최소 간격이 1시간이라 "마지막 사용" 표시가 최대 1시간 늦을 수 있다("약 N시간 전" 표기 권장). `user_agent`는 원문 문자열이라 프론트가 "iPhone Safari" 등으로 가공해 보여야 한다.
11. **`logout-all`.** 2절의 문구 차이 참고. 호출 후 현재 기기도 로그아웃되므로 응답 처리 후 상태를 비우고 로그인 화면으로.
12. **현재 사용자 정보·비밀번호 변경 API 없음.** 설정 화면에 "로그인한 아이디" 표시나 비밀번호 변경이 필요하다면 변경 제안이 필요하다. PLAN 설정 화면 목록에는 없으므로 의도된 범위로 본다.
13. **계정 복구 절차.** 인증 앱과 복구 코드를 모두 잃으면 로그인할 방법이 없고, 가입 API는 가입 후 비활성화된다. 서버에서 처음 상태로 되돌리는 절차(DB 백업 후 사용자 삭제 → 가입 토큰 설정 → 다시 가입)를 Phase 8 운영 문서(`deploy/README.md`)에 적는다.

## 10. 사람이 직접 확인할 것

- 로컬에서 README 순서대로 uvicorn을 띄우고 curl로 `/api/health`, `/api/auth/status`, `POST /api/auth/setup`(토큰 포함)을 호출한 뒤 인증 앱(Google Authenticator 등)으로 가입·로그인을 끝까지 해 본다. 테스트는 가짜 시계를 쓰므로 실제 30초 간격 TOTP와 인증 앱 호환(QR 인식, 코드 일치)은 사람이 확인해야 한다.
- 실제 인증 앱에서 QR(`data:image/svg+xml`)이 스캔되는지, 수동 입력 `secret`으로도 등록되는지.
- 배포 후 두 번째 배포(같은 SHA 재실행)에서 배포 직전 백업이 WAL 모드 DB에서도 성공하는지(`deploy.sh` backup 단계의 integrity_check·헤더 확인). 첫 Phase 4 배포 이후 처음 드러난다.
- 서버 재배포 후 진행 중이던 가입 대기·로그인 2단계가 처음부터 다시 시작되는 동작(메모리 상태)이 사용 흐름에서 거슬리지 않는지.
- (Phase 6 이후) 실기기 아이폰 PWA에서 쿠키 유지(400일), 홈 화면 앱 재실행 후에도 로그인 유지, 자동 대문자·인증 코드 자동 채움 동작.
