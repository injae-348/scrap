## 6. Phase 3에서 다룰 것 (미정 사항)

1. **서버 파일 갱신 방식 (가장 큰 미정 사항).** `docker-compose.yml`과 `deploy/deploy.sh`는 root 소유 755/644이고 `deploy` 사용자는 sudo가 없다. 따라서 배포(`deploy.sh`)가 이 파일들을 갱신할 수 없고, 저장소에서 compose를 바꾸면 사람이 `sudo install`을 해야 한다. 정할 것: (a) 손으로 갱신하되 PR에 "서버 파일 갱신 필요"를 표시, (b) compose·deploy.sh를 이미지에 넣고 배포 때 꺼내 쓰기(단 root 소유 보호는 약해짐). 어느 쪽이든 `deploy.sh` 첫 설치는 `sudo install`이고, 설치 전에는 5단계 키 접속이 실패하는 것이 정상이다.
2. **APP_UID.** api Dockerfile에서 UID를 10001로 고정하거나 README의 `chown`을 바꾼다. `data/`는 700이라 UID 불일치 시 SQLite를 열지 못한다. 헬스체크만 통과하는 빈 앱은 DB를 열지 않으므로 이 문제를 놓칠 수 있다. 첫 실제 앱 배포 때 반드시 확인한다.
3. **DB 백업 방식.** 호스트의 `deploy`는 `data/`를 읽지 못한다. 컨테이너 안에서 `sqlite3 .backup`/Python `sqlite3.Connection.backup`을 실행하고 `backups/`로 꺼내는 방법(예: `docker compose exec api ...` 후 `docker cp`, 또는 `backups/`를 api에 추가 마운트)이 필요하다. 추가 마운트 시 `backups/`의 소유자(deploy, 750)와 UID 충돌을 같이 정한다. 호스트에 `sqlite3`는 설치돼 있지만 `data/`를 직접 읽을 수는 없다.
4. **롤백용 직전 태그 기록 위치.** `.env`의 `IMAGE_TAG`를 고치지 말고(600, deploy 소유라 가능하긴 하다) `/opt/scrap-app/` 아래 별도 상태 파일에 현재·직전 SHA를 기록한다. `.env`의 `IMAGE_TAG`는 0000... 자리표시자라 수동 `docker compose` 실행 시 pull이 실패한다. 이는 의도된 방어이며 README 수동 복구 절차에 설명한다.
5. **uvicorn proxy headers.** Caddy가 `X-Forwarded-For/Proto`를 붙이므로 uvicorn에 `--proxy-headers --forwarded-allow-ips`로 compose 내부 네트워크 대역(또는 web 컨테이너 IP)만 신뢰하도록 지정한다. 안 하면 로그인 실패 제한이 모든 요청을 Caddy IP 하나로 보게 되고, Secure 쿠키·리다이렉트 판단도 어긋난다. 모든 곳(`*`)을 신뢰하지는 않는다. api는 `expose`만 쓰므로 외부에서 직접 접근할 수 없다.
6. **`depends_on` 조건.** 지금은 `web`이 `api`의 시작만 기다린다. 첫 요청이 502일 수 있으므로 `condition: service_healthy`를 검토한다. 배포 후 헬스체크는 api 직접이 아니라 Caddy를 거친 `https://<도메인>/api/health`로 해야 인증서·프록시까지 검증된다.
7. **GHCR pull 토큰.** `deploy` 사용자의 `docker login ghcr.io`(read:packages)는 아직 안 했다. 패키지를 처음 push하면 비공개가 기본이므로 공개/비공개 정책을 정한다. 공개 저장소라 이미지를 공개로 두면 로그인이 필요 없지만, 이미지에 비밀값이 들어가지 않는지 확인해야 한다.
8. **`.env.example` 보강 후보.** 백엔드가 확정되면 쿠키 `Secure` 설정, 허용 출처, AI 모델명 같은 변수를 추가한다. 단 SESSION_SECRET 등 api 전용 변수는 web에 넘기지 않는 현재 구조를 유지한다.
9. **컨테이너 하드닝 (선택).** `read_only: true` + tmpfs, `cap_drop: [ALL]`(web은 80/443 바인딩에 `NET_BIND_SERVICE` 필요)을 api에 먼저 시도한다.
10. **배포 워크플로 승인.** `deploy.yml`·`deploy.sh` 변경 PR은 CLAUDE.md 규칙대로 "⚠️ 배포 경로 변경" 표시. `DEPLOY_KNOWN_HOSTS`는 README 5-4의 `known_hosts` 한 줄 형식을 쓰되, `<접속 주소>`를 `DEPLOY_HOST`와 똑같이 맞춘다.
11. **API.md.** `GET /api/health` 추가 요청(위 2번 표 참고).
