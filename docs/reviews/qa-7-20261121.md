### 4-2. 명세와 구현의 어긋남

- 없음. 아래는 어긋남이 아니라 알아 둘 동작이다.
- [참고] **본문이 없는 요청도 분당·하루 한도 계산에는 "예약"으로 잡힌다.** `begin()`이 가져오기 전에 자리를 예약하므로(`limits.py:76-89`), 분당 10회가 이미 찬 상태에서는 "본문을 못 가져오는 URL"도 200 `content_fetched:false` 대신 429를 받는다. 횟수에는 세지 않으므로 API.md의 "횟수 집계 제외"와는 모순이 아니다. 문서에 한 줄 적어 두면 오해가 없다.
- [참고] **`/ai/extract`의 413은 사실상 1MB 초과에서만 난다.** 붙여넣은 본문이 50,000자를 넘으면 서버는 413이 아니라 400 `invalid_input`을 돌려준다(`router.py:112-113`). 프론트는 `maxLength=50000`으로 미리 막으므로(`ScrapEditorPage.tsx:642`) 화면에서 413 문구("붙여넣은 본문이 너무 길어요.")에 닿을 일은 거의 없다. 방어용으로 남아 있어 문제는 없다.

### [참고] 항목

- P-1. **한도 도달·사용 불가 이후에도 "AI로 채우기" 버튼은 활성** 상태다(`ScrapEditorPage.tsx:581-590`, `disabled`는 429 대기뿐). 누를 때마다 서버를 부르고, 한도 도달(503 `ai_quota_exceeded`)은 호출 횟수에 센다. API.md는 "재시도 버튼 없이"라고만 해서 위반은 아니다. 불편하면 이 두 코드에서 버튼 옆에 안내만 두거나 일정 시간 잠그는 방안을 정한다.
- P-2. **진행 표시 줄이 375px에서 접힌다.** `AiStatus.tsx:34`가 한 줄 `flex`라 "AI가 비슷한 표현까지 여러 번 검색하고 있어요…"(약 24자)는 폭이 남는 약 120px에서 3줄이 된다. `flex-wrap`으로 취소 버튼을 아래줄로 보내거나 문구를 줄이면 좋다.
- P-3. **검색에서 같은 질문을 다시 누르거나, 오류 뒤 "검색" 버튼을 눌러도 아무 일이 없다.** `ask()`(`SearchPage.tsx:44-50`)가 같은 쿼리 키로 `setSp`를 부르므로 `staleTime: Infinity` 캐시(성공)나 오류 상태가 그대로다. 성공 결과 재사용은 호출 절약이라 의도로 보이나, 오류 후에는 "다시 시도" 버튼으로만 다시 보낼 수 있다는 점이 입력줄에서는 드러나지 않는다.
- P-4. **페이지가 새로 불러와지면 검색이 자동으로 다시 간다.** `queryKey`가 질문이고 질문이 주소(`?q=`)에 있으므로, 새로고침·브라우저 복원·즉석 주소 열기 때 AI 호출(최대 90초, 횟수 1회)이 다시 일어난다. 오류 상태였던 질문으로 상세에서 돌아와도 같다. iOS 홈 화면 앱이 백그라운드에서 돌아오며 페이지를 다시 불러오는지는 11절 A에서 본다. 문제가 되면 질문을 주소에 두되 자동 실행 대신 "이 질문으로 검색" 버튼을 거치게 하는 방안이 있다(브라우저 저장소는 `security.test.ts` 규칙상 쓰지 않는다).
- P-5. **기존 메모가 있을 때 AI 메모 제안 확인 상자가 4줄만 보여 준다**(`ScrapEditorPage.tsx:472` `line-clamp-4`). 2,000자까지 올 수 있는 제안을 끝까지 보지 않고 "이 제안으로 바꾸기"를 눌러 기존 메모 전체를 대체하게 된다. "제안 되돌리기"로 복구는 되지만(`undoAi`), "펼쳐 보기" 또는 "메모 끝에 추가"가 있으면 안전하다.
- P-6. **AI가 제안한 마감일이 과거여도 그대로 채운다.** 서버는 "실제 날짜"만 검사한다(`router.py:207-213`). 마감 지난 배지로 보이므로 사용자가 알아볼 수 있다. 필요하면 안내 한 줄.
- P-7. **취소 직후 같은 요청을 다시 보내면 동시 처리 제한(429, `Retry-After: 5`)을 만날 수 있다.** 프론트의 429 안내(`AiStatus.tsx`)가 이미 이 경우를 보여 준다. 실기기에서 취소 → 바로 재시도해 문구가 자연스러운지만 본다(11절 A).
- P-8. **미리보기와 본문 추출의 동시 가져오기 자리가 각각 2개(인스턴스별)**라 합쳐 최대 4개다(`preview.py:152`, `pagetext.py:113`). API.md의 "같은 안전한 연결 구현 재사용"은 충족한다. 1코어 서버에서 부담이 되는지는 R-4 확인 때 함께 본다.
- P-9. **스크랩이 0개일 때 AI 검색 안내가 없다.** 호출 1회가 소모되고 "관련 스크랩을 찾지 못했어요."만 나온다. 스크랩 수를 알고 있으면(`useScraps`) 호출 전에 "아직 저장한 스크랩이 없어요"로 막을 수 있다.
- P-10. **삭제한 스크랩이 캐시된 AI 검색 결과에 남을 수 있다.** 결과는 `['ai','search',query]` 캐시(`staleTime: Infinity`)에 있고 스크랩 삭제·수정 후 이 캐시를 무효화하는지 정적으로 확인하지 못했다(`hooks/queries.ts`). 삭제 후 카드를 누르면 "스크랩을 찾을 수 없어요"로 처리되므로 치명적이지는 않다.
- P-11. **붙여넣은 본문이 아닌데 `content_fetched:false`가 오는 "붙여넣은 본문으로는 파악하지 못했어요" 분기**(`ScrapEditorPage.tsx:612-616`)는 서버가 붙여넣은 본문에 `false`를 돌려주지 않으므로 도달하지 않는다. 방어 코드로 남겨도 되고 정리해도 된다.

## 11. 사람이 직접 확인할 것

### A. 실제 키로 (로컬 개발 또는 배포 직후, PC에서 먼저)
1. **채우기 1회**: 일반 기사 링크 → "AI로 채우기". 제목·마감일·메모(한국어 마크다운)·주제가 입력칸에 채워지고 "AI 제안" 배지가 붙는지, **저장하기 전에는 목록에 생기지 않는지**. 소요 시간(진행 표시의 경과 시간)을 기록.
2. **검색 1회**: 스크랩 5개쯤 저장한 뒤 "이런 공모전 찾아줘" 같은 질문. 결과 카드와 이유, 소요 시간, 동의어 검색을 여러 번 하는지(서버 로그에 도구 호출 횟수는 남지 않는다).
3. **본문을 못 가져오는 링크**(로그인 필요한 페이지, X·당근 등): `content_fetched:false` 안내 → 본문 붙여넣기 → 다시 채우기.
4. **유튜브 링크**(R-3): 본문 붙여넣기 없이 채우기. 제목이 영상 제목으로 오고 엉뚱한 요약(동의 화면 문구 등)이 오지 않는지.
5. **마감일 상대 표현**: "이번 주 금요일까지"가 든 글을 붙여넣어 날짜가 맞게 풀리는지.
6. **키를 넣기 전 배포 상태의 오류 화면**(키 없는 서버 `.env`): 두 화면에서 "AI 기능을 사용할 수 없어요 (서버 설정 필요)"가 나오고 일반 저장·목록은 정상인지. 월 한도 도달 문구는 실제로 재현하기 어려워 단위 테스트로만 확인된 상태다.
7. **한도**: 분당 10회를 넘기는 빠른 반복 요청(쉬운 방법은 `.env`에 `AI_PER_MINUTE=2` 같은 낮은 값을 임시로 두고 로컬에서 확인)에서 429 안내와 남은 시간 표시.
8. **Anthropic Console 사용량**과 서버 로그에 키·본문·검색어가 남지 않았는지.

### B. 배포 직후 서버에서 (사용자, 마스터는 서버 접속 금지)
1. 채우기·검색 직후 api 컨테이너 메모리 사용량(`docker stats --no-stream`)이 한도(384MB) 안인지, 컨테이너가 재시작되지 않았는지(R-4).
2. 로그(`docker compose logs api`)에 "Claude API 호출 실패"·"본문 가져오기 예외" 같은 경고가 반복되지 않는지. 명령은 `deploy/README.md`의 운영 절차에 맞춰 사용한다(비밀값이 펼쳐지는 진단 명령은 쓰지 않는다).
3. 첫 배포 뒤 `https://<이름>.duckdns.org/api/health`가 정상이고 `/api/ai/*`가 미인증이면 401인지.

### C. 실기기 아이폰(홈 화면 앱, HTTPS 운영 도메인)
1. 링크 붙여넣기 → AI로 채우기 → 진행 표시·취소 버튼(터치 영역)·채워진 제안·"제안 되돌리기"·저장까지 한 번에.
2. **AI 요청 중 앱을 백그라운드로 보냈다가 돌아왔을 때**: 요청이 이어지는지, "네트워크에 연결할 수 없습니다"가 나오는지, 그 뒤 다시 누르면 정상인지(서버는 이미 횟수를 셌을 수 있음). 검색 화면에서도 같게(P-4: 돌아왔을 때 질문이 자동으로 다시 전송되는지).
3. **본문 붙여넣기**: 긴 본문(수천 자) 붙여넣기 시 iOS의 "붙여넣기 허용" 안내, 글자 수 표시, 50,000자 근처에서의 반응, 키보드가 올라온 상태에서 입력칸·저장 바 위치.
4. **AI 검색 탭**: 예시 질문 칩, 한글 입력(IME 조합 중 엔터), 진행 중 표시(375px에서 문구가 접히는 모양, P-2)와 "검색 취소", 결과 카드 탭 → 상세 → 뒤로 가기에서 결과가 유지되는지.
5. **새 주제 제안**: "새 주제 제안" 칩을 눌러야만 주제가 만들어지는지, "무시" 버튼, 이미 있는 주제가 대소문자 달라도 선택 상태로 들어오는지.
6. **메모 링크 호스트 표시**: AI가 만든 메모와 직접 쓴 메모의 링크 옆에 호스트가 작게 보이는지, 긴 호스트가 줄 바꿈되는지, 다크 모드 대비.
7. **다크 모드**: 경고 톤(한도 도달)·오류 톤(서버 설정 필요)·점선 제안 박스·"AI 제안" 배지.
8. 취소 직후 바로 다시 요청했을 때 429 문구가 자연스러운지(P-7).
