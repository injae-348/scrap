## 3. 실패 / 위험 항목

### 3-1. [실패, PR 전 필수] 서버 `.env`에 `DB_PATH`가 들어간다는 보장이 없다 → 첫 배포가 헬스체크에서 실패할 수 있다

- 위치: `docker-compose.yml` api 서비스(`environment`에 `DB_PATH` 없음), `backend/app/config.py`(기본값 `./data/dev.db`), `deploy/README.md` 6절·11절·12-0, `.env.example`.
- 근거: `config.py` 주석은 "운영에서는 compose가 DB_PATH를 지정한다"고 하지만 compose는 지정하지 않고 `env_file: .env`로만 받는다. 서버 `.env`는 Phase 2에서 당시 `.env.example`을 복사해 만든 것이다. 이번 PR이 `.env.example`에 `DB_PATH`·`TZ`를 추가했지만 이미 만들어진 서버 `.env`에 옮기라는 절차가 11절·12절 어디에도 없다. 6절 표도 "IMAGE_TAG, ANTHROPIC_API_KEY 등은 예시값 그대로"까지만 말한다.
- 재현: 서버 `.env`에 `DB_PATH`가 없는 상태로 배포하면 앱은 `./data/dev.db`(컨테이너 `/app/data`, 루트 읽기 전용, 폴더 없음)를 열려다 `/api/health` 503 → api 컨테이너 unhealthy → `docker compose up` 실패 → 첫 배포라 롤백 대상이 없어 실패로 끝난다 (사이트는 이미 꺼진 상태라 추가 피해는 없지만 첫 성공이 막힌다). 반대로 `.env`에 있으면 통과하므로 지금 서버 `.env` 내용을 이 검토에서는 확인할 수 없다 (확인 불가).
- 수정 제안 (둘 중 하나, 1번 권장):
  1. compose api에 `environment: { DB_PATH: /data/scrap.db }`를 고정한다. 볼륨 대상(`/data`)과 한 파일 안에서 계약이 맞고, `.env` 누락·오타에 영향받지 않는다. `config.py` 주석과 `.env.example`의 `DB_PATH` 설명도 맞춘다. (compose는 "서버 파일"이므로 11절로 설치된다.)
  2. 최소한 12-0에 `chk ".env 에 DB_PATH=/data/scrap.db"`와 `chk ".env 에 IMAGE_TAG 자리표시자"`를 추가하고, 없을 때 넣는 명령(편집기 안내)을 적는다.
- 같은 맥락: `deploy.sh`의 백업 스크립트는 `DB_PATH` 기본값을 `/data/scrap.db`로 쓰고 앱 기본값은 `./data/dev.db`로 서로 다르다. 1번으로 고정하면 해소된다.

### 3-2. [확인 필요, PR 전 권장] 0바이트(빈) DB에서의 백업

- 위치: `deploy/deploy.sh` BACKUP_PY, `backend/app/db.py`.
- 근거: `/api/health`는 `sqlite3.connect()` 후 `SELECT 1`만 실행하므로 첫 배포 뒤 `scrap.db`는 쓰기 없이 열려서 0바이트 파일일 가능성이 높다. 두 번째 배포의 `backup_db`는 이 파일을 `src.backup(dst)`로 복사하고 결과가 `SQLite format 3` 헤더로 시작하는지 검사하며, 아니면 "배포를 중단한다". SQLite의 backup API는 원본이 0페이지일 때 대상에 빈 DB(헤더 포함)를 만들도록 알고 있어 통과할 것으로 보이나, deploy.sh 하네스는 가짜 docker라 이 경로를 실제 sqlite로 검증하지 못했다. 헤더 검사가 실패하면 **두 번째 배포부터 앞으로 계속 막힌다** (Phase 4에서 첫 쓰기가 생길 때까지).
- 확인 방법 (마스터, 로컬): 빈 파일 하나를 만들어 `BACKUP_PY`와 같은 코드로 backup → 결과 파일 크기와 첫 15바이트를 확인한다. 이미지 안에서 `docker run --rm -v <빈 폴더>:/data <api 이미지> python -` 형태로 하면 더 정확하다. 실패하면 헤더 검사를 "0바이트이면 건너뜀"으로 완화한다.

### 3-4. [권장] 문서·표현

- README 12-0이 `data/` 소유(10001, 700)를 확인하지만 ❌일 때의 수정 명령이 없다. `sudo chown 10001:10001 /opt/scrap-app/data && sudo chmod 700 /opt/scrap-app/data`를 옆에 적는다.
- compose 네트워크 서브넷이 기존 Docker 네트워크와 겹치면 `Pool overlaps` 오류가 난다. 주석에는 있으나 README 12-3 실패 시 안내에 한 줄 필요 (대역을 바꾸면 compose·`--forwarded-allow-ips`·web IP 세 곳을 함께).
- `DEPLOY_USER` 값이 `deploy`라서 GitHub이 로그 전체에서 단어 `deploy`를 `***`로 가린다. `deploy.sh`의 로그 접두어(`... deploy: ...`)와 경로(`/opt/scrap-app/deploy/`)도 가려져 읽기 어렵다. 시크릿이 아닌 Environment **변수**(`vars`)로 옮기거나, 감수하고 12-3에 "`***`로 보이는 것은 정상"이라고 적는다. 12-1(c)의 "시크릿 4개" 확인도 함께 바뀐다.
- `PLAN.md` 설계의 `authorized_keys` 예시(`command=...,no-port-forwarding,...`)와 README 5-2(`restrict,command=...`)가 다르다. 실제는 README 쪽이 맞으므로 PLAN 예시를 맞춘다 (마스터 수정).
- `.env.example`에 `ENABLE_API_DOCS`(운영에서는 켜지 않음)가 없다. 주석으로 한 줄 넣어 두면 설정 존재를 알 수 있다.
- `deploy.yml`의 이미지 이름은 `github.repository_owner`에서 만들고, compose에는 `injae-348`이 하드코딩돼 있다. 현재 값이 같아 문제는 없다 (계정명은 이미 공개). 소유자가 바뀌면 두 곳을 함께 고쳐야 한다는 주석은 이미 있다.
- 첫 배포가 성공하면 `https://<이름>.duckdns.org`에 **Phase 1의 목(mock) 데이터 UI**가 인증 없이 공개된다 (`frontend/src/api/index.ts`가 아직 전부 mock 호출). 가짜 데이터라 정보 유출은 아니지만 "개발용 섹션·목 모드 문구"(qa-1에서 Phase 6으로 넘긴 것)가 보인다. 사용자가 알고 있어야 한다.

## 10. 사람이 직접 확인할 것

- 병합 후 첫 Deploy 실행에서 `test`·`build`가 초록인지, 액션 SHA 고정이 모두 유효한지 (로그에 "unable to resolve action"이 없는지).
- GHCR 패키지 2개가 저장소 `scrap`에 연결되고 공개 전환 후 로그인 없이 pull 되는지 (12-3).
- 승인 후 `deploy` 잡 로그 끝에 `배포 성공`과 `외부 헬스체크 통과`가 나오는지, 공개 로그에 도메인·IP가 `***`/`x.x.x.x` 외로 보이지 않는지.
- 시크릿 창으로 `https://<이름>.duckdns.org`가 임시 페이지 대신 앱 화면을 보이는지, 인증서를 새로 받지 않는지 (12-4).
- 서버 재부팅 후 컨테이너 자동 시작, DuckDNS cron 재개, `iptables` 유지 (qa-2에서 이월).
- `docker stats`·`free -m`으로 api 384MB, web 128MB 한도 내 동작 (12-4 판정 줄이 대신해 주지만 첫 배포 직후 한 번은 눈으로).
- 두 번째 배포(같은 SHA 재실행 또는 다음 PR)에서 백업 단계와 상태 파일 갱신이 정상인지 — 3-2가 이 시점에 드러난다.
- 롤백 경로는 실제로 실패한 배포가 없으면 검증되지 않았다. 안전한 시험으로, 일부러 헬스체크가 실패하는 커밋을 올려 보는 것은 사용자 판단 (사이트가 잠시 내려갈 수 있음).
