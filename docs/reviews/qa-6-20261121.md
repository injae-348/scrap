### 지적

- [권장] **R-1. 편집하는 동안 다른 기기에서 주제나 출처를 지우면 저장이 계속 실패한다.** 위치: `ScrapEditorPage.tsx:352-360`. 재현: 편집 화면(또는 새 스크랩)에서 주제 A를 선택한 채로, 다른 브라우저에서 설정으로 주제 A를 삭제하고, 첫 화면에서 "저장"을 누른다. 서버가 없는 주제 id를 400 `invalid_input`으로 거부한다. 화면은 `onError`에서 주제·출처 목록을 다시 받지만, 선택 상태(`topicIds`, `sourceId`)에는 지워진 id가 그대로 남아 있어 화면에서는 칩이 사라져 보이는데도 저장할 때마다 같은 오류("입력값이 올바르지 않습니다.")가 난다. 출처도 같다(선택값이 목록에 없어 `<select>`가 빈 칸). 제안: 저장 직전에 `topicIds`를 현재 `topics` 목록에 있는 id로 거르고, 출처는 목록에 없으면 `null`(새 스크랩이면 자동 판별) 또는 기본 출처로 돌린다. 목록을 새로 받은 뒤에 바뀐 선택을 알리는 한 줄("지워진 주제를 뺐어요")이 있으면 좋다.
- [권장] **R-2. 새 버전 "새로고침"이 작성 중인 내용을 지울 수 있다.** 위치: `UpdatePrompt.tsx:40`(`update(true)`), 주석 `:8`. `update(true)`는 페이지를 다시 불러오는데, 작성 중 보호(`beforeunload`)는 아이폰 홈 화면 앱에서 확인 창이 안 뜰 수 있다(실기기 확인 필요, 9절). 편집 화면에서 "새 버전이 있어요"가 뜨면 사용자가 눌러 입력이 사라질 수 있다. 제안: 편집 중 변경 여부(`dirty`)를 가벼운 전역 상태로 공유해, 변경이 있으면 "새로고침" 대신 안내 문구("저장한 뒤 새로고침해 주세요")만 보여 주거나, 누르면 `LeaveDialog`를 거치게 한다. 주석의 "브라우저의 이탈 확인이 한 번 더 뜬다"도 실기기 결과에 맞춰 고친다.
- [권장] **R-3. 목록 요청이 400 `invalid_input`이면 "다시 시도"가 해결하지 못한다.** 위치: `BrowsePage.tsx:129-135`. 재현: 검색어에 단어를 11개 이상 넣거나, 주소창에서 `?q=`에 제어문자·201자 이상, `?topics=`에 101개 이상을 넣는다(서버가 400, 검색어 규칙은 API.md "검색 q"). 입력칸은 `maxLength=200`만 막는다. 같은 요청을 다시 보내므로 계속 실패한다. 제안: `isApiError(list.error, 'invalid_input')`이면 서버 문구 + "검색어·필터 모두 해제" 버튼(`update({ q: '', sourceId: undefined, topicIds: [] })`)을 보여 준다. 검색어 단어 수(10개)도 입력 단계에서 안내하면 더 좋다.
- [권장] **R-4. 이미 받은 데이터가 있어도 다시 받기 실패 하나로 화면 전체가 오류 화면으로 바뀐다.** 위치: `BrowsePage.tsx:131`(`list.isError`), `ScrapDetailPage.tsx:37`(`q.isError`), `AppLayout.tsx:33`(`status.isError`). TanStack Query는 데이터가 있어도 마지막 요청이 실패하면 `isError`가 true라서, 저장·삭제 뒤 목록 재조회나 상세 재진입 때 잠깐 네트워크가 끊기면 보고 있던 목록·상세가 사라진다. 재현: 개발자 도구에서 네트워크를 끊고 목록 화면에서 좋아요 토글 후 다른 목록을 오가거나 상세에서 "수정" 후 다시 진입. 제안: 오류 화면 조건을 `isError && !data`로 좁히고, 데이터가 있으면 상단에 "최신 상태를 불러오지 못했어요 · 다시 시도" 한 줄만 보인다.
- [참고] **좋아요 모아보기에서 하트를 해제해도 그 항목이 목록에 남는다.** 위치: `hooks/queries.ts:156-160`(`refetchType: 'inactive'`라 지금 보는 목록은 다시 받지 않음). 실수로 해제했을 때 바로 다시 누를 수 있어 의도로 보이며, 다른 화면에 갔다 오면 사라진다. "좋아요 모아보기" 동작 설명에 맞는지만 사용자가 확인한다.
- [참고] **스크랩 저장 직후 이동이 목록 재조회가 끝나야 일어난다.** 위치: `hooks/queries.ts:111-114`에서 `onSuccess`가 `invalidateQueries`의 Promise를 돌려주므로 화면 쪽 `onSuccess`(이동·토스트)가 그 뒤에 실행된다. 스크랩이 많거나 느린 연결에서는 저장 버튼 스피너가 길어진다. 상세는 `setQueryData`로 이미 채웠으므로 `void qc.invalidateQueries(...)`로 기다리지 않아도 된다.
- [참고] **목록 메모 미리보기가 마크다운 링크 중간에서 잘리면 원문이 보인다.** 위치: `ScrapListItem.tsx:10-18`. 서버가 300자에서 자르므로 `[제목](https://...`처럼 닫는 괄호가 없는 조각은 정규식에 걸리지 않아 그대로 보인다. 코드 펜스는 `|$`로 처리돼 있다. 표시만 거슬리는 정도다.
- [참고] **모바일에서 "마감 임박"으로 가는 링크가 "전체" 화면에만 있다**(`BrowsePage.tsx:54-62`). 탭바는 PLAN대로 4개라 괜찮고, 좋아요 화면에서는 "마감순" 정렬로 대신한다. 불편하면 사용자가 판단한다.
- [참고] **메모 입력칸 `maxLength=100000`은 글자(UTF-16) 단위, 서버는 문자 단위라** 이모지가 많은 메모는 서버 한도보다 먼저 막힌다(안전한 쪽). 붙여넣은 긴 글이 조용히 잘리는 점만 인지.
- [참고] **AI 404를 "준비 중"으로 바꾸는 처리(`api/index.ts:98-107`)는 Phase 7에서 지운다.** 남기면 서버가 진짜 404를 돌려줄 때도 같은 문구가 나온다.
- [참고] **`ui-builder.md`에 목 데이터 안내가 남아 있다**(`.claude/agents/ui-builder.md` 3행 설명의 "목 데이터 프로토타입", 38~39행 "목 데이터 단계 (Phase 1)", `src/mocks/`). 목이 삭제됐으니 "이력"으로 표시하거나 지우면 다음 Phase에서 혼동이 없다(마스터가 직접 수정 가능한 문서).
- [참고] **화면 단위 테스트가 인증·API·마크다운·URL·폼 변환에 몰려 있다.** 목록(커서 초기화, `invalid_input` 복구), 편집(제목 `null` 안내, 미리보기 늦은 응답 무시, 이탈 경고), 설정(`duplicate_pattern` 필드 오류)은 테스트가 없다. R-1·R-3 수정 때 함께 추가하면 좋다.

## 9. 사람이 직접 확인할 것 (실기기 아이폰)

HTTPS 운영 도메인에서, 배포 뒤에 확인한다. 클립보드 읽기는 HTTPS에서만 동작한다.

1. **홈 화면 추가**: Safari에서 공유 → "홈 화면에 추가". 아이콘(책갈피 모양, 모서리 검은 띠 없음)과 이름("스크랩")이 맞는지. 실행하면 주소창 없는 전체 화면으로 열리는지.
2. **앱에서의 로그인 상태**: 홈 화면 앱은 Safari와 쿠키가 따로일 수 있다. 앱에서 로그인한 뒤 앱을 완전히 종료하고 다시 열어도 로그인이 유지되는지, 며칠 뒤에도 유지되는지. 로그인할 때 인증 코드를 같은 30초 안에 다시 쓰면 거부되는 안내가 보이는지.
3. **클립보드 "링크 붙여넣기"**: 링크 복사 → 앱 → "링크 붙여넣기". iOS의 "붙여넣기 허용" 안내가 뜨고, 허용하면 링크가 채워지고 제목·출처가 자동으로 채워지는지. 거부했을 때, 클립보드에 링크가 없을 때 문구가 나오고 링크 칸이 활성화되는지, 그다음 칸을 길게 눌러 붙여넣기가 되는지. 공유 문구에 섞인 링크도 뽑히는지.
4. **안전 영역**: 노치·다이내믹 아일랜드 아래로 헤더가 안 가려지는지, 홈 인디케이터 위로 하단 탭바·"+" 버튼·저장 바가 겹치지 않는지, 가로 모드에서 좌우 여백. 상태 표시줄(`default`)과 다크 모드 조합에서 글자가 읽히는지, 상단 색 띠가 앱 배경과 어색하지 않은지.
5. **키보드**: 편집 화면에서 키보드가 올라올 때 저장 바 위치, 입력칸 포커스 시 화면이 확대되지 않는지(16px), 마감일 `date` 입력칸 모양, 6자리 코드 칸의 숫자 키패드·인증 코드 자동 채움(`one-time-code`), 아이디 칸에 자동 대문자가 붙지 않는지.
6. **업데이트 안내**: 새 버전을 배포한 뒤 앱을 열어 "새 버전이 있어요"가 뜨는지, "새로고침"을 눌렀을 때 새 화면이 되는지, "나중에"를 누르면 계속 쓸 수 있는지. **편집 중에 안내가 뜬 상태에서 "새로고침"을 눌렀을 때 입력이 사라지는지(R-2)**.
7. **홈 화면 앱 시작 화면**: 실행할 때 흰 화면이 잠깐 보이는지(다크 모드에서 눈부심). 시작 화면 이미지는 없다.
8. **4줄 고정 헤더(6절)**: 작은 아이폰에서 목록이 충분히 보이는지. 긴 제목·긴 URL·메모 수백 줄의 카드와 상세.
9. **다크 모드 대비**: 시스템 다크로 바꾼 뒤 배지(AI 제안·마감 임박), 점선 제안 박스, 비활성 버튼, 토스트.
10. **한글 입력**: 검색창에서 IME 조합 중에는 요청이 가지 않고 엔터·지우기에서만 가는지(`BrowsePage.tsx` `SearchBox`), 이미지·긴 메모 저장 속도.
11. **복구 코드 보관**: 가입 직후(또는 재설정) 코드를 "모두 복사"해서 비밀번호 관리자 등에 붙여 넣을 수 있는지, 길게 눌러 직접 선택해도 되는지.

## 10. Phase 7 이후로 넘길 것

Phase 7 (AI)
1. `POST /ai/extract`, `POST /ai/search` 연결: 지금 프론트는 404를 "준비 중"으로 바꿔 보여 준다(`api/index.ts:98-107`) — 연결 때 이 분기를 지우고 실제 오류 코드(`ai_*`)를 API.md에 정한다.
2. `POST /ai/search` 결과의 `scrap` 형식을 정한다(4-2). 전문 `Scrap`이면 응답이 커질 수 있으므로 `ScrapListItem`(`memo_preview`)로 통일하는 쪽을 권한다. 프론트 `SearchPage.tsx`는 `memo`를 쓰지 않는다.
3. AI 채우기 응답의 주제 제안은 이미 있는 주제 이름과 대소문자 무시로 맞추고, 없는 이름은 "AI가 제안한 새 주제"로 표시하며 자동 생성하지 않는다(`ScrapEditorPage.tsx:290-296`) — 서버가 이름을 정규화해 주는지 맞춘다.
4. 본문 붙여넣기 크기(Caddy 5MB, 앱 1MB 한도)와 `payload_too_large` 문구("내용이 너무 길어서 저장할 수 없어요. 메모를 줄여 주세요")가 AI 채우기에도 맞는지.

Phase 8 (운영)
1. 배포 뒤 첫 확인: `/api/health`, 로그인, 스크랩 저장, 정적 파일 응답 헤더(11절).
2. 프론트 의존성 정기 점검 방안은 별도 문서(비공개) 참고.
3. PWA 업데이트 정책: 새 버전 적용 시점(R-2 후속), 서비스워커 캐시 정리가 잘 되는지 몇 번의 배포 뒤 확인.

PLAN에 옮길 것 (마스터)
- Phase 6 체크박스: 충족 8개는 사용자 확인 뒤 체크, 3·4번(홈 화면 추가, 클립보드)은 9절을 마친 뒤. 또는 두 항목만 남기고 PR을 병합한다.
- Phase 6에 R-1~R-4를 같은 PR에서 고칠지 후속으로 미룰지 결정. 필수는 없다.
- Phase 7: 이 문서 10절 1~4번.
